    readme_url duplicate

    The refined anti-spam logic:

    Use this:

    1. Honeypot filled → block immediately

    2. Same raw README URL already active → block as likely duplicate project

    3. Same email + same repo URL + same project title within 10 minutes → block as likely duplicate submission

    4. Same browser submits again within 60 seconds → frontend cooldown

    5. IP hash → store/log for abuse visibility, but do not block yet

    ## Technical and Security Metadata

    When users submit a Builder Showcase project or interact with site forms, DataInsideData™ may process limited technical metadata to support security, abuse prevention, troubleshooting, and platform reliability.

    This may include:

    • browser or user-agent information
    • request origin or referring page
    • submission timestamps
    • form validation results
    • hashed network identifiers used for abuse detection

    DataInsideData™ does not store raw IP addresses for Builder Showcase submissions. When network-level abuse signals are needed, the platform may store a salted hash instead of the raw address. This helps identify repeated abusive behavior without casually storing the original network address.

    This technical metadata is used for purposes such as:

    • preventing spam or duplicate submissions
    • protecting the submission workflow
    • diagnosing form or platform errors
    • maintaining the quality and reliability of the Builder Showcase

    This information is not used to sell personal data or create advertising profiles.

    What –preserve-existing means now

    With the updated publisher.py, the behavior should be:

    Find public DB project by slug → load existing YAML → merge incoming DB project with existing YAML → if same slug exists and –preserve-existing is used, keep the existing YAML record → write full YAML file → generate only the page for that slug → log exported_to_yml and detail_page_generated

    So if ai-review-sentiment-labeling-pipeline already exists in _data/builder_projects.yml, this flag should prevent the DB version from overwriting that existing YAML record.

    You should expect a message like:

    Preserved existing project, skipped duplicate slug: ai-review-sentiment-labeling-pipeline Page generation scoped to 1 filtered project(s). Important nuance

    Even with –preserve-existing, the page may still regenerate from the preserved YAML record. That is fine if your goal is:

    keep YAML data unchanged but rebuild the detail page from the existing YAML record

    If we want to preserve the YAML record and not regenerate the page, use:

    python scripts/export_builder_project.py --slug ai-review-sentiment-labeling-pipeline --preserve-existing --no-pages

    Insert Submission Flow

    → if insert error, return 500 → if no data returned, return 500 → if insert succeeded, log submission_created → return success to frontend

    Enterprise-style Safety Detail

    • submission insert succeeded
    • event logging failed → do not tell the user the whole submission failed

    Final flow

    bad insert → return 500

    insert succeeds but no row returned → return 500

    insert succeeds and row returned → attempt event log

    event log works → return 201

    event log fails → log server error, still return 201

    Github Essentials

    Stop copying full repo folders into branches unless it’s a last-resort recovery move.

    Best recovery move now

    Before merging anything, run this on your current branch:

    git status

    If you see changes you want to keep, commit them:

    git add .
git commit -m "Checkpoint current builder showcase work"

    If you are not sure whether the changes are clean yet, create a safety branch first:

    git switch -c safety/current-recovery-checkpoint
git add .
git commit -m "Safety checkpoint before branch cleanup"

    That gives you a restore point.

    Clean merge strategy

    I’d pick one integration branch where everything comes together, maybe:

    feat/community-projects

    Then merge the other feature branches into it:

    git switch feat/community-projects
git pull origin feat/community-projects

git merge feat/add-posts
git merge feat-builder-staging

    If Git reports conflicts, that is not failure. That is Git saying:

    “These branches touched the same area. Please choose the final version.”

    After resolving conflicts:

    git add .
git commit

    Then push:

    git push origin feat/community-projects

    Before any merge, inspect what will come in

    This is the confidence builder:

    git diff --name-status feat/community-projects..feat/add-posts

    That shows what feat/add-posts has that feat/community-projects does not.

    And:

    git diff --name-status feat/community-projects..feat-builder-staging

    That shows what staging has that community projects does not.

    My recommendation

    Make a checkpoint first, then use Git merges — not copy/paste — from here forward.

    safest flow:

    git status
git switch -c safety/pre-merge-cleanup
git add .
git commit -m "Safety checkpoint before merging feature branches"

git switch feat/community-projects
git merge feat/add-posts
git merge feat-builder-staging

    Then test locally:

    bundle exec jekyll build --config _config.yml,_config_staging.yml --destination_site_staging_full
